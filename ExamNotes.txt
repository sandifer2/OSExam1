Safety: nothing bad happens, no crash or data overwrite
Liveness: eventually something good happens, like the producer getting to work again 
Fairness: everyone gets a turn 

Deadlock: processes are perma blocked because each holds anothers resource needed to get unblocked 
4 Deadlock Conditions: if we can break any 1 of these, we can prevent deadlocks entirely 
Mutual Exclusion: only one process can use a resource at a time (all share resource, no waiting)
Hold and Wait: a process is holding at least one resource and is waiting to acquire additional resources held by other processes 
No Preemption: Resource cannot be forcibly taken from a process; they must be released voluntarily 
Circular Wait: A closed chain of processes exists, where each process holds a resource needed by the next process in the chain

Deadly Mix: Deadlock vs Starvation 
Deadlock: a group of processes are all stuck waiting for each other. no one can ever move 
Starvation: a process is able to run, but the scheduler keeps picking those with higher prio or shorter completion time 

How to Handle deadlocks
- Prevention: design the system so that one of the 4 requirements can never occur 
- Avoidance: OS proactively checks every resource request to ensure it wont lead to an unsafe state 
- Detection and Recovery: let them happnen, find them when they occur, and fix them

**Dispatching Loop & Threads
- A thread owns a Thread Control Block
    - has execution state, status(run or sleep), scheduling(prio ie MLFQ)
- Threads are run from a Dispatching Loop (per CPU thread/background)
LOOP(Context Switch):
- Run -> Save -> Choose a new thread to run (scheduling) -> Load states from a different thread 
How does the dispatcher regain control?
- Internal event: Yield (voluntarily), thread waiting for IO, thread waiting for another thread
- External Event: Interrupts, complete storage request, Timer (RR)
What should a thread save?
- Anything that the next thread may trash before a context switch, program counter, registers, changes in execution stack
How does the dispatcher choose the next thread?
- keeps a list of ready threads, none ready = loop
- if more than one, use scheduling policy

** Preemptive vs Nonpreemptive Scheduling 
- main difference is who deceides when a process stops using the CPU 
Nonpreemptive: process keeps running on the CPU until finishes or gets blocked (IO) or yields. Voluntarily gives up CPU
Preemptive: the scheduler can force a process to leave the CPU even if it hasnt finished, allowing another process to run 
    - triggered by timer interrupts



**CPU Scheduling Algorithms 
- FIFO - first in first out, the process to arrive first is the first to run 
- SJN - shortest job next, pick the job that will take the least amount of time (may starve)
- RR - round robin, give each process a small slice(Time Quantum) of cpu time and rotate through them 
- SRTF - shortest remainig time first, a preemptive version of SJN, if a shorter time job arrives, switch to it immediately (may starve)

Multilevel Feedback Queue (MLFQ) - used by real OS 
- Multiple Queues: tasks are organized into several queues with different priority levels
- Priority Rule: the scheduler always the job from the highest - priority queue first 
- Feedback: The OS adjusts a tasks priority based on its past behavior 
    - we favor interactive(i/o) over CPU bound tasks

Lottery Scheduling - give more tickets to shorter CPU time jobs, less to higher cpu time jobs, run lottery and 
run job whose ticket was called

**Implementing Locks 
1. Disabling Interrupts(Uniprocessor) - Aquire and Release
    - make operations atomic by preventing context switch 
    - Aquire() disables interrupts, Release() enables them 
    - Busy-Waiting: check if value is FREE, if not, enable interrupt to allow other threads to run before reenabling interrupt 
    - Problem: User level may never re enable interrupts, OS lose control, doesnt work on multiprocessor, cpu cores can enter still 
2. Atomic Hardware Instructions (test_and_set)
    - test_and_set atomically reads a mem location, sets it to 1 (BUSY) and returns old value 
    - Implemenataion: thread calls while(test_and_set(value)==1), busy waits until val becomes 0 
    - hogs CPU cycles 
3. No Busy Waiting - Waiting Queues 
 - put threads to sleep rather than busy waiting 
    - if lock is not FREE, thread is added to waiting queue and goes to sleep 
    - when a thread releases the lock, it checks the queue, if another thread is waiting, wake them up and place them in ready queue 
    - multiprocessor version: use guard to minimize busy waiting while we manage queue and lock value 
**Semaphores vs Integers 
- No Negative Values 
- Only have 2 operations P(take) and V(give)
    - cannot read or write directly except during intial setup 
- Cannot read or write semaphore values, Except at the initialization times
- Operations are atomic
    - Two P() calls cannot decrement the value below zero
    - A sleeping thread at P() cannot miss a wakeup from V()

**2 Uses of Semaphores 
1. Mutual Exclusion 
    - only one thread can access a critical section at a time 
    - init value = 1, call P() to lock before critical section, V() to release 
2. Scheduling 
    - used to coordiante the order of exeecution between different threads 
        - init value = 0 
        - one thread waits at a P() operation until another thread signals it is ready by calling V() 

** Producer/Consumer : Bounded Buffer 
- 3 Semaphores
    - mutex = 1, only 1 thread manipulates buffer at a time 
    - nFreeBuffers = N, tracks empty spaces, producer waits until the buffer is full
    - nLoadedBuffers = 0, tracks items in buffer, consumer waits if buffer is empty 

correct Producer/Consumer 
// Semaphore full = 1;  (Counts full slots)
// Semaphore empty = 0; (Counts empty slots) usually N not 0 
// Semaphore mutex = 1; (Protecting the buffer)
//Standard Producer code
void Producer(){
    P(empty);
    P(mutex);
    // Add item to buffer 
    V(mutex);
    V(full);
}
// Standard Consumer code
void Consumer() {
    P(full);   // Wait for a full slot full = 0 
    P(mutex);  // Lock the buffer [cite: 74, 75] mutex alr = 0 
    
    // Remove item from buffer
    
    V(mutex);
    V(empty);
}



** Definitions**
Operating system – a virtual machine that hides the complexity and limitations of hardware from application programmers
Job – A unit of processing for the operating system (commonly batch systems)
Batch system – a system that collects a batch of jobs before processing them and printing out results
Timesharing –  a system design goal allowing each user to afford terminals to interact with machines, optimizing for the efficient use of human resources

Thread – a sequential execution stream and the smallest CPU scheduling unit. It can be programmed as if it owns the entire CPU.
Address space -  Contains all states necessary to run program,
Includes code, data, stack, program counter, register values and resources required by the program.
Process – an address space plus at least 1 thread of execution. 
    - It is a fundamental unit of computation
Context switch – The process of saving the state of a running process and restoring the state of the next process to run

Uniprogramming – running one process at a time 
Multiprogramming – running multiple processes on a machine 
Multithreading – having multiple threads per address space
Multiprocessing – running programs on a machine with multiple processors(or a multicore processor)
Multitasking – a single user can run multiple processes

Master boot record – describes the physical layout of the disk and fits into a single 4K-byte disk sector (boot sector). It is stored at the first logical sector of the boot device 
System call – allows processes running at the user mode to access kernel functions that run under the kernel mode 
User mode – a mode where an application can only access its own address space
Kernel mode – a mode where anything goes (full access to hardware and resources)

Starvation – a state where a thread waits indefinitely 

Atomic operation – an operation that always runs to completion; its all or nothing, we cant save and resume
Race condition – a situation in cooperating threads where the outputs depends on the order and timing of the execution 

Mutual exclusion – a property ensuring that at most one thread is in the critical section at any time 
Critical section – the segment of code where shared resources are accessed or modified

Busy waiting – hogging CPU cycles while a thread is waiting for a lock 

Semaphore – a type of generalized lock consisting of a nonnegative integer value and two atomic operations, P(free) and V(give)

Safety – at most one thread is in the critical section at any time 
Liveness – if more than one thread is interested in executing the critical section, processes will eventually do so
Fairness – every thread that wants to execute the critical section will eventually do so (no starvation)
